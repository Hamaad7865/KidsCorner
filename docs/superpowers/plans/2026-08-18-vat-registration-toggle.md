# VAT Registration Toggle Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add a shop-wide VAT registration toggle, defaulted off with a saved 15% rate, while freezing the applicable VAT policy on every completed sale, return, received purchase, receipt, and report so historical records never change.

**Architecture:** Treat VAT registration as an append-only policy ledger. A privileged database RPC atomically creates each new policy, updates the current settings pointer, and records one activity event. Transactional RPCs resolve and freeze a policy before calculating VAT; readers use only frozen fields. The web back office owns policy administration, while Android receives the current policy through bootstrap, refreshes it before trading, and attaches the immutable policy identity and checkout time to each sale request.

**Tech Stack:** Next.js 16, React 19, TypeScript, Supabase/Postgres, Vitest, Kotlin, Jetpack Compose, kotlinx.serialization, JUnit, Android Emulator.

**Spec:** [2026-08-18-vat-registration-toggle-design.md](../specs/2026-08-18-vat-registration-toggle-design.md)

## Global Constraints

- The current VAT policy is append-only. Never edit a historical policy row.
- The configured rate is stored as a decimal fraction (`0.15` means 15%).
- Disabled policies retain their configured rate but expose an effective rate of zero.
- Legacy cached Android bootstrap data decodes as VAT enabled at its cached rate.
- Legacy queued sale payloads may omit policy fields; the server maps only missing/null policy IDs to the immutable legacy policy.
- A supplied non-null policy ID that is unknown, future-dated, or otherwise invalid must fail. It must never fall back to the current policy.
- The first idempotent checkout attempt freezes `vat_policy_id` and `checked_out_at`; all retries reuse the exact request.
- Sale totals remain VAT-inclusive. Toggling VAT changes the tax split, not the amount payable.
- Returns copy and reverse the original sale's VAT snapshot, regardless of current policy.
- Received purchases freeze the policy effective when they are received. Draft purchases do not become tax ledger entries.
- Historical browser and Android receipts, credit notes, Z reports, daily summaries, VAT returns, journals, P&L views, and exports read frozen transaction data only.
- New database objects must have explicit RLS policies and explicit grants. No application client receives mutation rights on `vat_policies`.
- Follow test-driven development for every task: add a failing test, observe the intended failure, implement the smallest complete change, and rerun the focused test before broad verification.
- Commit after each task with only that task's intended files staged.
- All database reads/tests/migrations target only the user-authorized `Kids Corner` test project ref `lfjfccxqlkhetbbcicjb`. Verify both `supabase/.temp/linked-project.json` and `mcp__codex_apps__supabase_get_project` before the first database call. If Supabase authentication is invalid, pause for reconnection; never substitute another project.

```sql
create table public.vat_policies (
  id bigint generated by default as identity primary key,
  enabled boolean not null,
  configured_rate numeric(7,6) not null check (configured_rate between 0 and 1),
  vat_number text,

) returns bigint
```

The migration also adds frozen VAT policy columns to `sales`, `credit_notes`, and `purchases`, plus an explicit VAT identity snapshot on closed Z reports. The current policy is the highest policy `id` (not a timestamp-only sort, which can tie). Use the existing project naming style, but preserve these semantics:

```text
sales:       vat_policy_id, vat_enabled, vat_rate, vat_number
credit_notes: vat_policy_id, vat_enabled, vat_rate, vat_number
purchases:   vat_policy_id, vat_enabled, vat_rate, vat_amount
z_reports:   vat_identity_snapshot JSON array of enabled policy ID/rate/number records
```

Each Z identity element has this stable JSON shape:

```json
{"policyId": 42, "rate": 0.15, "vatNumber": "TEST-VAT-001"}
```
